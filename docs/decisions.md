# Журнал архитектурных решений

Каждое решение записывается в формате: контекст → решение → последствия.
Решения не удаляются; если решение меняется, добавляется новая запись со ссылкой на старую.

## ADR-001. Rust + Cargo workspace со слоями Clean Architecture
- **Контекст:** приложение должно быть на Rust, следовать SOLID и Clean Code и расширяться новыми играми.
- **Решение:** отдельные крейты `domain`, `application`, `infrastructure`, `games/*`, `app-desktop`.
- **Последствия:** границы слоёв проверяет компилятор: крейт не может использовать то, от чего не зависит. Шаблонного кода чуть больше.

## ADR-002. SQLite вместо PostgreSQL (2026-11-14)
- **Контекст:** приложение должно быть portable и запускаться без установки. PostgreSQL — отдельный сервер.
- **Решение:** встраиваемая БД SQLite в одном файле внутри `data/`.
- **Последствия:** нет внешних процессов, минимум памяти. Доступ к БД скрыт за портами,
  поэтому другую БД можно подключить новой реализацией в `infrastructure`.

## ADR-003. Tauri 2 + Svelte 5 + TypeScript для интерфейса (2026-11-14)
- **Контекст:** важен гибко настраиваемый визуал, темы, похожесть на Paimon.moe.
- **Решение:** Tauri (системный WebView2) с интерфейсом на Svelte и TypeScript.
- **Последствия:** вся логика на Rust, интерфейс — тонкий слой отображения.
  Нужна синхронизация версий Tauri в Rust и npm (см. development.md).
  Для работы нужен WebView2, он встроен в Windows 10/11.

## ADR-004. Portable-режим по умолчанию, задел под установщик
- **Решение:** `StorageMode::Portable` хранит данные в `data/` рядом с `.exe`.
  `StorageMode::UserProfile` хранит их в `%APPDATA%\WishCounter`, переключение — константа в `bootstrap.rs`.
  В `tauri.conf.json` уже настроены установщики NSIS/MSI (`npm run app:build:installer`).

## ADR-005. Темы — CSS-переменные, тема в ядре хранится строкой
- **Решение:** `ThemeId` — проверенная строка (`a-z0-9-`, до 32 символов). Тема добавляется без изменения Rust-кода.

## ADR-006. Локализация на собственном модуле
- **Решение:** словари `ru.ts` / `en.ts` без внешней библиотеки. Тип `Record<TranslationKey, string>` проверяет при компиляции, что все строки переведены.

## ADR-007. Настройки в JSON, а не в БД
- **Решение:** `data/settings.json`. Файл можно читать и править вручную, а при повреждении базы тема и язык не сбрасываются. Запись атомарная (временный файл + переименование).

## ADR-008. Rust установлен в C:\Rust
- **Контекст:** в пути профиля пользователя есть кириллица (`C:\Users\Елена`), а некоторые инструменты сборки не работают с не-ASCII путями.
- **Решение:** `RUSTUP_HOME=C:\Rust\rustup`, `CARGO_HOME=C:\Rust\cargo`.

## ADR-009. Тесты в отдельном файле рядом с кодом (2026-11-15, ревью владельца)
- **Контекст:** тесты внутри `mod tests { ... }` удлиняют файлы с кодом. Вариант `foo.rs` + `foo/tests.rs`
  запутывал: код и тесты лежали в разных местах.
- **Решение:** модуль с тестами — папка `foo/` с двумя файлами: `foo.rs` и `foo.tests.rs`.
  ```rust
  // в родителе (lib.rs или mod.rs):
  #[path = "foo/foo.rs"]
  pub mod foo;

  // в конце foo/foo.rs:
  #[cfg(test)]
  #[path = "foo.tests.rs"]
  mod tests;
  ```
  Для корня крейта — `lib.rs` + `lib.tests.rs`. Тесты фронтенда (с этапа 5) — `*.test.ts` рядом с кодом.
- **Последствия:** код и его тесты всегда лежат в одной папке. Для Rust это нестандартная раскладка
  (обычно используют `foo/mod.rs` или `foo.rs` + папку `foo/`), поэтому каждому такому модулю нужен `#[path]`.
  Тесты — дочерний модуль и через `use super::*` видят приватные элементы.
  Тесты только публичного API при необходимости можно писать в папке `tests/` крейта.

## ADR-010. Стили компонентов — в теге `<style>` внутри `.svelte` (2026-11-15, ревью владельца)
- **Контекст:** пробовали вынести стили в отдельные файлы `*.module.css` (CSS Modules).
- **Решение:** вернуть стандартный подход Svelte — `<style>` внутри компонента.
  Компилятор Svelte сам ограничивает эти стили компонентом.
- **Отклонённая альтернатива:** CSS Modules. Они требуют `class={styles.x}` вместо `class="x"`, не работают с директивой
  `class:`, а селекторы по тегам в них глобальны.

## ADR-011. Пулы баннеров и расчёт гаранта в домене (2026-11-15, этап 2)
- **Контекст:** у разных игр разные коды баннеров и числа гаранта, но сама логика (счётчики, 50/50) общая.
- **Решение:** общий расчёт (`PityTracker`) находится в `domain::pity`. Игра описывает только данные:
  список `PoolDefinition` (коды баннеров с общим счётчиком, `PityRules`, цена молитвы).
  Проверка «с баннера ли 5★» вынесена в трейт `FeaturedLookup`. Его реализация на справочниках появится на этапе 4,
  а пока используется `NoFeaturedData`.
- **Последствия:** HSR и ZZZ добавляются как данные плюс собственный `FeaturedLookup`, расчёт не меняется.

## ADR-012. Вероятности — целые числа в сотых долях процента
- **Решение:** `Probability(u32)`, где 5500 = 55%. Целые числа сравниваются точно и одинаково сериализуются,
  а форматированием занимается интерфейс (`formatChance`).

## ADR-013. Исход 50/50 неизвестен — статус «неизвестен», а не догадка
- **Решение:** если хотя бы для одного 5★ в пуле нет данных о баннере, `FeaturedStatus::Unknown`.
  Показывать гарант по неполным данным опаснее, чем не показывать его.

## ADR-014. Vitest подключён на этапе 2 (раньше плана)
- **Контекст:** в интерфейсе появилась логика: форматирование, подстановка параметров, выбор текста 50/50.
- **Решение:** Vitest 5 использует `vite.config.ts`, тесты лежат в `*.test.ts` рядом с кодом, запуск — `npm test`.
  Логика вынесена из `.svelte` в `.ts`-модули, чтобы её можно было тестировать без компонентов.

## ADR-015. rusqlite (bundled) и собственные миграции (2026-11-15, этап 3)
- **Контекст:** нужна встраиваемая БД без установки. Варианты: `rusqlite` (синхронный) или `sqlx` (async).
- **Решение:** `rusqlite` с `bundled`: SQLite компилируется в .exe (+1,6 МБ).
  Async не нужен, потому что база локальная, а Tauri и так выполняет команды в пуле потоков. Соединение одно, под `Mutex`.
  Миграции написаны вручную (`PRAGMA user_version` + SQL-файлы через `include_str!`): около 40 строк, внешняя библиотека не нужна.
  Режим WAL: запись не блокирует чтение, а сбой при записи не портит базу.
- **Последствия:** база от более новой версии приложения не открывается (`DatabaseError::NewerSchema`),
  чтобы старый код её не испортил. Выпущенные миграции не меняются никогда.

## ADR-016. Сквозные тесты — в `tests/` крейта
- **Решение:** проверки стыковки слоёв (SQLite → сервис → правила игры) лежат в `crates/app-desktop/tests/`.
  Это исключение из ADR-009: такие тесты проверяют связку крейтов, а не один модуль, и видят только публичный API.

## ADR-017. Данные WebView2 — в `data/webview` (2026-11-15)
- **Контекст:** по умолчанию WebView2 хранит кэш в `%LOCALAPPDATA%\com.wishcounter.desktop\EBWebView`.
  Portable-приложение не должно оставлять следов вне своей папки.
- **Решение:** в `tauri.conf.json` у окна стоит `"create": false`. Окно создаётся в `window.rs` через
  `WebviewWindowBuilder::from_config(...).data_directory(paths.webview_dir)`.
- **Последствия:** все параметры окна по-прежнему задаются в `tauri.conf.json`. Новые окна нужно создавать
  тем же способом, с `data_directory`.

## ADR-018. Размер .exe: картинки и WebView2 не встраиваются (2026-11-15, решение владельца)
- **Решение:** в .exe встраиваются только код, интерфейс, SQL-миграции и небольшие справочные данные (JSON).
  Картинки персонажей и оружия хранятся в `data/` (кэш), WebView2 берётся из Windows.
- **Последствия:** .exe остаётся небольшим (около 7 МБ). Чтобы картинки были доступны офлайн, их нужно один раз скачать или
  положить рядом в архиве дистрибутива (решается на этапах 4 и 10).

## ADR-019. Справочник — данные Paimon.moe через собственный разборщик (2026-11-15, этап 4a-1)
- **Контекст:** у HoYoverse нет публичного API расписания баннеров. Автор Paimon.moe поддерживает данные вручную
  (лицензия MIT). Файлы — JavaScript-модули, а не JSON.
- **Решение:** собственный разборщик JS-литералов (`game_genshin::paimon::js_literal`) **только читает значения**
  и ничего не выполняет: скачанный код не запускается. Глубина вложенности ограничена (64).
  Конвертер переводит данные в наш формат `ReferenceSnapshot` (идентификаторы Paimon.moe сохраняются — это важно для импорта).
  Расхождения `-`/`_` в идентификаторах Paimon.moe выравниваются автоматически.
- **Последствия:** если Paimon.moe поменяет формат файлов, упадёт `data-sync` или обновление (4b), но не приложение:
  встроенный снимок останется рабочим.

## ADR-020. Встроенный снимок справочника генерируется командой `data-sync`
- **Решение:** `cargo run -p data-sync` скачивает файлы последней ревизии Paimon.moe и пишет
  `crates/games/genshin/data/reference.json` (≈190 КБ, форматированный JSON — удобно смотреть изменения в git).
  Файл встраивается в .exe через `include_str!`. **Вручную файл не правится.**
  Атрибуция и лицензия MIT — в `THIRD_PARTY_NOTICES.md` и в настройках приложения.

## ADR-021. Политика сетевых запросов
- **Решение:** `HttpClient` (ureq + rustls): только HTTPS, только `raw.githubusercontent.com` и `api.github.com`,
  без перенаправлений, тайм-аут 30 с, ответ не больше 8 МБ. Файлы скачиваются по ревизии (40 hex-символов,
  проверяется перед подстановкой в адрес), чтобы все файлы обновления были согласованы.

## ADR-022. Сервер игрока хранится в профиле игры в базе (2026-11-15, этап 4a-2)
- **Контекст:** по решению владельца сервер выбирается вручную или читается из JSON Paimon.moe (вариант «Б»).
- **Решение:** таблица `game_profiles` (миграция 0002), порт `ProfileRepository`, `ProfileService`.
  Сервер хранится в базе, а не в `settings.json`: он относится к аккаунту и его истории, а не к приложению.
  Время баннеров пересчитывается так же, как в Paimon.moe (docs/genshin-rules.md), с запасом 1 минута на конце баннера.
- **Последствия:** пока сервер не выбран, исход 50/50 «неизвестен», и интерфейс просит выбрать сервер.

## ADR-023. Проверка «с баннера ли предмет» — общая, а не в модуле игры
- **Решение:** метод `GameModule::featured_lookup` удалён. `ScheduleFeaturedLookup` (домен) строится из справочника,
  пулов игры и сервера в `StatisticsService`. Для новой игры достаточно данных справочника.

## ADR-024. Одно соединение с базой на все хранилища
- **Решение:** `SharedConnection` (`Arc<Mutex<Connection>>`) создаётся в `bootstrap.rs` и передаётся всем
  SQLite-хранилищам. Два соединения к одному файлу тоже работали бы (WAL), но одно проще и экономнее.

## ADR-025. Онлайн-обновление справочника (2026-11-17, этап 4b)
- **Решение:**
  - отдельный трейт `RemoteReference` (источник и сборка справочника) вместо новых методов в `GameModule`
    (разделение интерфейсов). `GameModule::remote_reference` имеет реализацию по умолчанию `None`;
  - `ReferenceService` хранит справочники под `RwLock` и умеет их заменять; `ReferenceUpdater` отвечает только за
    обновление (единственная ответственность);
  - сначала запрашивается только ревизия (1 маленький запрос), файлы скачиваются, лишь если она изменилась;
  - новый справочник проверяется: не пустой и не меньше половины текущего по числу предметов;
  - при запуске выбирается более новый из встроенного и скачанного (по `generated_at`): после обновления
    самого приложения старый скачанный справочник не «перекроет» более свежий встроенный;
  - автопроверка — в отдельном потоке при запуске, не чаще раза в сутки; кнопка — команда `async` +
    `spawn_blocking`, чтобы окно не зависало; об обновлении интерфейс узнаёт по событию `reference-updated`.
- **Последствия:** `data-sync` использует тот же загрузчик и тот же список файлов, что приложение.

## ADR-026. Общие функции записи JSON
- **Решение:** `infrastructure::json_file` (`read_json`, `write_json_atomically`) — одна реализация атомарной записи
  для настроек и кэша справочников вместо копий.

## ADR-027. Сервер игрока — на странице «Импорт»; задел под фон приложения (2026-11-18, решение владельца)
- **Контекст:** сервер нужен для истории молитв, а не для просмотра статистики; переключатель-табы на странице игры
  занимает место и непонятен без пояснения.
- **Решение:**
  - на этапе 6 выбор сервера переносится на страницу «Импорт» (выпадающий список + иконка «i» с подсказкой);
    при импорте JSON Paimon.moe сервер берётся из файла. До этапа 6 временно остаётся `RegionSelector` на странице игры;
  - пустая история → сообщение с переходом на «Импорт»;
  - фон приложения — CSS-переменная `--app-background-image` (заложена сейчас, по умолчанию `none` — внешний вид не меняется),
    выбор фона в настройках — этап 5, после кэша картинок (4c).
- **Последствия:** ядро менять не нужно — сервер по-прежнему сохраняется через `ProfileService`.

## ADR-028. Картинки — через собственный протокол `wcimg` и кэш на диске (2026-11-18, этап 4c)
- **Контекст:** картинки не встраиваются в .exe (ADR-018); нужны офлайн после первого показа; у интерфейса не должно
  быть доступа к файлам и сети.
- **Решение:**
  - асинхронный протокол Tauri `wcimg`: `<img src>` → Rust → кэш `data/cache/images/<игра>/<предмет>.png` или GitHub;
  - скачиваются только картинки **предметов из справочника**, по пути из `RemoteReference::image_path`, из той же ревизии,
    что справочник; ответ проверяется на сигнатуру PNG, размер ≤ 2 МБ;
  - CSP: `img-src` дополнен `wcimg: http://wcimg.localhost`; права (`capabilities`) не расширялись;
  - неудачные запросы запоминаются до конца сеанса, чтобы не повторять их при каждой перерисовке.
- **Последствия:** `ItemIcon` пригоден для таблицы молитв (этап 5); тот же механизм подойдёт для своих фонов (этап 5).
  Модуль `json_file` переименован в `files` (теперь и для байтов), проверка безопасных имён файлов — в нём.

## ADR-029. Ключевые арты версий как фоны, иконки игр, страница-справочник (2026-11-18, пожелания владельца)
- **Фоны:** для Genshin встроенный набор фонов — ключевые арты каждой версии. Список версий берётся из справочника,
  сами картинки скачиваются по требованию и хранятся в `data/backgrounds/genshin/` (не в .exe). Источник и условия
  использования проверяются в начале этапа 5.
- **Иконка игры** в левом меню рядом с названием — этап 5.
- **Страница-справочник** (персонажи, оружие, версии, баннеры) — отдельный этап 11, после основного плана по Genshin:
  данные уже есть в справочнике (этап 4).

## ADR-030. Порядок этапов, иконки игр, тесты компонентов (2026-11-18, этап 5a)
- **Порядок (решение владельца):** 5a → этап 6 (импорт) → 5b (таблица) и 5c (фоны) — на настоящих данных.
- **Иконка игры:** файл владельца (128×128, 31 КБ) встраивается в модуль игры (`crates/games/<игра>/assets/icon.png`, `include_bytes!`,
  `GameModule::icon_png`), чтобы быть видимой с первого запуска офлайн. Маленькая иконка не противоречит ADR-018
  (запрет касается больших наборов картинок). Отдаётся тем же протоколом: `wcimg://…/games/<игра>/icon`;
  у картинок предметов адрес теперь `/items/<игра>/<предмет>`.
- **Тесты компонентов:** @testing-library/svelte + jsdom в Vitest (`test.environment = 'jsdom'`, в тестах сборка Svelte
  с условием `browser`), очистка страницы после каждого теста — `ui/src/test-setup.ts`.
- **Select** построен на стандартном `<select>` (клавиатура, экранный диктор, системный список — бесплатно);
  **InfoTooltip** — кнопка «i» + `role="tooltip"`, видна при наведении и фокусе с клавиатуры.
